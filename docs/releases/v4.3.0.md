# Uni Schedule v4.3.0 — Experience & Communication Update

- **Базовий реліз:** `v4.2.1` (`3b4b1e57f26d7846b4b8e4362c487e71801bc33f`)

## 1. Реалізовані можливості (Stages A–E)

### Нова анімація запуску — Hybrid №25 «Signature Calendar Reveal» (Stage A)
- Повна програмна реалізація затвердженого референсу **Hybrid №25 (3000 мс)** у світлій та темній темах (`AppSplash.tsx`):
  - **Phase A (`sunrise`, 0–650 мс):** композиція Quiet Sunrise із бурштиновим диском, тонкою аркою, лінією горизонту та словознаком `Uni Schedule`.
  - **Phase B (`date`, 650–1150 мс):** безперервний морфінг бурштинового диска в активну плитку реальної поточної дати (без хардкоду `ЧТ 26`).
  - **Phase C (`calendar`, 1150–1750 мс):** поява сусідніх реальних днів робочого тижня навколо активної дати.
  - **Phase D (`reveal`, 1750–2450 мс):** фірмове вигнуте хвильове розкриття (`clip-path: ellipse(...)`) у реальний інтерфейс розкладу.
  - **Phase E (`settle`, 2450–3000 мс):** м'яке встановлення інтерфейсу та синхронізована поява `BottomNav`; завершення рівно на `3000 мс`.
- Підтримка `prefers-reduced-motion` (~320 мс), 0 порожніх стартових кадрів, 0 повторних запусків при зміні вкладок, адаптивність для `320px–1280px` та 100% робота офлайн.

### «Що нового?» та «Історія оновлень» (Stage C)
- Реалізовано модальне вікно **«Що нового?»** (`WhatsNewModal.tsx`) та **«Історія оновлень»** (`UpdateHistoryModal.tsx`) на базі `ModalDrawer`.
- Строге SemVer-порівняння (`4.10.0 > 4.9.0`, `4.3.1 > 4.3.0`), розрізнення `installedVersion` vs `latestPublishedRelease`, збереження статусу перегляду (`seenReleaseIds`), безпечний rollback і відсутність блокування онбордингу для нових користувачів.
- Повна підтримка офлайн-доступу до каталогу релізів.

### Сповіщення про оновлення та дедуплікація (Stage D)
- Додано незалежний opt-in перемикач **«Новини та оновлення»** (`release_updates_enabled`, за замовчуванням **вимкнено** для всіх користувачів).
- Адитивна D1-міграція `0010_release_communication.sql`: `release_updates_enabled`, таблиці `releases` і `release_notification_deliveries` із `PRIMARY KEY (release_id, user_id)` (максимум 1 логічна доставка на користувача для релізу, детермінований вибір 1 активної підписки при multi-device, обмежені ретраї `attempt_count < 3`, обробка HTTP `404/410`).
- Service Worker `v15` передає same-origin deep links (`/?view=release&version=X.Y.Z`) у вже відкрите вікно або через `openWindow` при cold launch.

### Єдине джерело метаданих та процес майбутніх релізів (Stage E)
- Канонічний каталог: `src/data/releases.ts` (спільний для frontend, Worker API `/api/releases*` і CLI `scripts/publish-release.ts`).
- Публічні read-only endpoints: `GET /api/releases`, `GET /api/releases/latest`, `GET /api/releases/:version` (приховують `draft`).
- Захищені admin endpoints: `POST /api/admin/releases/publish`, `POST /api/admin/releases/dispatch` (вимагають `Authorization: Bearer <RELEASE_ADMIN_TOKEN>`, fail-closed `503` без токена, `dryRun: true` за замовчуванням).

## 2. Інструкція для майбутніх релізів

1. **Додати метадані релізу:** додати запис у `RELEASES_CATALOG` у `src/data/releases.ts` зі статусом `publicationStatus: 'draft'`, `publishedAt: null`.
2. **Локальний dry-run:**
   ```bash
   npx tsx scripts/publish-release.ts --version=4.4.0 --dry-run
   ```
3. **Розгортання:** після деплою Worker + Vercel і перевірки `SW` та health-чеків явно опублікувати реліз:
   ```bash
   RELEASE_ADMIN_TOKEN=... API_BASE_URL=https://uni-schedule-api.lev68819.workers.dev \
     npx tsx scripts/publish-release.ts --version=4.4.0 --publish --confirm-live
   ```
4. **Dry-run розсилки push (0 мутацій БД, 0 push):**
   ```bash
   RELEASE_ADMIN_TOKEN=... API_BASE_URL=https://uni-schedule-api.lev68819.workers.dev \
     npx tsx scripts/publish-release.ts --version=4.4.0 --dispatch --dry-run
   ```
5. **Запуск розсилки (лише після погодження власника):** додати `--confirm-live` до `--dispatch`. Повторний запуск автоматично пропустить користувачів із записом `sent`/`expired` у `release_notification_deliveries` і повторить лише `failed` (`attempt_count < 3`).
